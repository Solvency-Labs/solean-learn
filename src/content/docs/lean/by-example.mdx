This is a *reading primer*, not a tutorial — enough to make the real files legible. For actually learning to write proofs, work through "Theorem Proving in Lean 4" (linked in [the previous page](/solean-learn/lean/)).

## Everything is a term with a type

Lean is built on dependent type theory. `x : T` reads "`x` has type `T`". Values, types, propositions, and proofs are all *terms*.

```lean
def n : Nat := 42              -- a natural number
def double (x : Nat) : Nat := x + x   -- a function
#eval double 21               -- 42
```

## Propositions are types; proofs are their terms

The mind-bending part: a **proposition** is a type, and a **proof** is a term of that type. `Prop` is the type of propositions.

```lean
def two_plus_two : 2 + 2 = 4 := rfl   -- `rfl` proves things true by computation
```

So "to prove `P`" literally means "to construct a term of type `P`". When Lean type-checks the term, the proof is checked.

## Theorems and tactics

Real proofs are built with **tactics** — a little imperative language for constructing the proof term. `theorem` (or `lemma`) states the goal; `by` enters tactic mode.

```lean
theorem add_comm_example (a b : Nat) : a + b = b + a := by
  rw [Nat.add_comm]   -- rewrite using a known lemma
```

Tactics you'll see constantly: `intro` (assume a hypothesis), `rw` (rewrite), `simp` (simplify), `cases`/`rcases` (split on constructors), `exact` (give the term directly), `apply` (use a lemma), `rfl` (close by computation).

## Inductive types (how models are built)

The project models contract data and statements as **inductive types** — closed sets of constructors. This is exactly how the EVM/Yul AST and the FORS structures are represented.

```lean
inductive Stmt where
  | skip   : Stmt
  | assign : Slot → Expr → Stmt
  | seq    : Stmt → Stmt → Stmt
  | require : Cond → Stmt
```

You read it as: "a `Stmt` is *either* a `skip`, *or* an `assign` of an expression to a slot, *or* a sequence of two statements, *or* a `require`." Functions over inductives are defined by **pattern matching** on the constructors, and proofs proceed by `cases` on them.

## Structures (records)

```lean
structure UserOp where
  opHash : UInt256
  nonce  : UInt256
  domain : UInt256
```

Field access is `op.nonce`. You'll see the FORS signature and the wallet state modeled as structures like this.

## A taste of a project-shaped theorem

The shape of theorems in this codebase is "**success implies the guards held**":

```lean
theorem validate_success_implies_nonce_ok
    (env : Env) (op : UserOp) (s : Storage)
    (h : validate env op s = .success s') :
    op.nonce = s.get nonceSlot := by
  ...
```

Read it as: *given* that `validate` returned success, we can *conclude* the nonce matched. That's the whole genre — and a finished FORS proof slots a real verifier into the `validate`-style story (see [SoLean](/solean-learn/tooling/solean/) and [the task](/solean-learn/task/)).

## Check yourself

<Question q="In `def two_plus_two : 2 + 2 = 4 := rfl`, name the proposition and the proof.">
The **proposition** (a type, of sort `Prop`) is `2 + 2 = 4`. The **proof** (a term of that type) is `rfl`. The `def` binds a name to a proof of that proposition. Proposition = type, proof = term — the whole trick of dependent type theory.
</Question>

<Question q="Given the inductive `Stmt` with constructors `skip`, `assign`, `seq`, `require`, how does a proof about a function over `Stmt` typically proceed?">
By **case analysis / induction on the constructors** (`cases` or `induction`). You show the property holds for `skip`, for `assign`, for `require`, and for `seq` (often using the induction hypotheses on its two sub-statements). Since the inductive is a *closed* set of constructors, covering all cases proves it for every `Stmt`.
</Question>

<Question q="Read the `validate_success_implies_nonce_ok` statement. What is *assumed*, and what is *concluded*?">
**Assumed:** the hypothesis `h : validate env op s = .success s'` — i.e. validation succeeded. **Concluded:** `op.nonce = s.get nonceSlot` — the nonce matched. It's the project's signature shape: *success implies the guard held*. The proof reasons backwards from "it returned success" to "every guard on that path must have passed."
</Question>

## How to actually read a `.lean` file

1. Find the **inductive types / structures** first — they're the vocabulary.
2. Find the **definitions** (`def`) — these are the model's behavior.
3. Read **theorem statements** before their proofs — the statement is the claim; the proof is just the (machine-checked) argument.
4. Don't get stuck on tactic details on a first read. *What is claimed* matters more than *how* it's discharged.
